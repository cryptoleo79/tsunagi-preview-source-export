# TSUNAGI Observability and Health

Complete reference for all observability subsystems, journals, JSON
endpoints, dashboards, and health scoring.

---

## 1. Journals

All journals are append-only NDJSON files. One JSON object per line.
Written by `src/net/ledger/journal.zig`.

### 1.1 journal.ndjson

Primary journal. Written during block processing.

**Entry types:**

```
roll_forward
  slot, block_no, tip_hash_hex, header_hash_hex, tx_count,
  utxo_count, utxo_consumed, utxo_produced, utxo_delta, ts

roll_backward
  slot, block_no, tip_hash_hex, ts

tx_decode
  slot, block_no, block_hash, tx_count, truncated,
  txs: [{idx, in, out, fee, meta}...]

slot_observation
  slot, block_no, observed_unix, kind, gap_from_prev_block

peer_event
  peer, event, slot, block_no, latency_ms, reason, ts
```

### 1.2 mempool.ndjson

Written when a transaction is submitted via POST /tx/submit.

```
mempool_tx
  txid, in, out, fee, meta, size, ts
```

### 1.3 confirmation.ndjson

Written when a pending mempool TX is found in a new block.

```
confirmed_tx
  txid, received_unix, confirmed_unix, confirmation_seconds,
  block_no, slot, fee
```

### 1.4 propagation.ndjson

Written when a locally submitted TX completes its lifecycle.

```
propagation_tx
  txid, local_submitted_unix, block_observed_unix,
  block_no, slot, confirmed_unix, confirmation_seconds
```

### Journal Pruning

Each journal has a corresponding prune script in `scripts/`:

| Script | Target |
|--------|--------|
| `prune-journal.sh` | `journal.ndjson` |
| `prune-confirmation.sh` | `confirmation.ndjson` |
| `prune-decode.sh` | TX decode entries |
| `prune-mempool.sh` | `mempool.ndjson` |
| `prune-network.sh` | Network entries |
| `prune-propagation.sh` | `propagation.ndjson` |
| `prune-slots.sh` | Slot observation entries |

## 4. Health Scoring

### 4.1 Engine

Two implementations exist that must stay in sync:

| Implementation | Location | Purpose |
|---------------|----------|---------|
| Zig | `src/net/health/health_engine.zig` | Canonical reference (pure computation) |
| Shell | `scripts/generate-health-json.sh` | JSON generator (mirrors Zig exactly) |

### 4.2 Component Scoring

All arithmetic is integer-only. No floating point.

**A. Peer Score (weight: 25%)**

```
Input:  connect_count, disconnect_count
Logic:  rate = disconnect * 100 / connect
        score = 100 - (rate * 70 / 100)
        If rate >= 100: score = 30
        If no data: score = 80 (neutral)
Range:  30 - 100
```

**B. Slot Score (weight: 20%)**

```
Input:  avg_gap (× 10 for integer, e.g., 1.5 → 15)
Logic:  ≤ 30 (3.0s): 100
        ≤ 100 (10.0s): linear 100→70
        ≤ 300 (30.0s): linear 70→40
        > 300: 40
        If no data: 80 (neutral)
Range:  40 - 100
```

**C. Block Score (weight: 25%)**

```
Input:  blocks_processed, rollbacks
Logic:  rate = rollbacks * 10000 / blocks_processed (capped at 1M)
        score = 100 - (rate * 60 / 100)
        If rate >= 100: score = 40
        If no blocks: 80 (neutral)
Range:  40 - 100
```

**D. Confirmation Score (weight: 15%)**

```
Input:  avg_confirmation_seconds
Logic:  ≤ 30s: 100
        ≤ 120s: linear 100→60
        ≤ 300s: linear 60→30
        > 300s: 30
        If no data: 80 (neutral)
Range:  30 - 100
```

**E. Mempool Score (weight: 15%)**

```
Input:  pending_count
Logic:  0: 100
        ≤ 10: 95
        ≤ 50: linear 95→70
        ≤ 200: linear 70→40
        > 200: 40
Range:  40 - 100
```

### 4.3 Composite Score

```
score = (peer*25 + slot*20 + block*25 + confirm*15 + mempool*15) / 100
```

### 4.4 State Thresholds

| Score | State | Meaning |
|-------|-------|---------|
| ≥ 90 | `excellent` | All components performing well |
| ≥ 75 | `healthy` | Normal operation |
| ≥ 60 | `degraded` | One or more components under stress |
| < 60 | `critical` | Significant issues detected |

## 5. Limitations

### Bounded, Not Complete

All runtime stores have fixed capacity. When full, oldest entries are
evicted. TSUNAGI does not index the full chain. It tracks only recent
events within capacity bounds.

| Store | Capacity | When Full |
|-------|----------|-----------|
| Delta history | 200 blocks | Oldest evicted |
| Block decode | 100 blocks | Oldest evicted |
| Mempool capture | 256 txs | Oldest evicted |
| Confirmation tracker | 256 pending + 256 confirmed | Oldest evicted |
| Slot observatory | 512 observations | Oldest evicted |
| Peer observatory | 512 events | Oldest evicted |

### Local Submissions Only

Confirmation correlation tracks only transactions submitted through
TSUNAGI's own HTTP endpoint. Transactions arriving from peers are not
tracked for confirmation latency.

### Journal Growth

Journals grow unboundedly. Pruning scripts must be run periodically
(via cron) to prevent disk exhaustion. Recommended retention: 24-48
hours for high-frequency journals.

### Health Score Freshness

Health scoring depends on JSON files generated by cron-scheduled scripts.
The score is only as fresh as the last generator run. Typical staleness:
10-60 seconds depending on cron interval.

### No Real-Time Streaming

Web pages poll JSON files via XMLHttpRequest. There is no WebSocket or
Server-Sent Events channel. Update latency = cron interval + poll interval.
